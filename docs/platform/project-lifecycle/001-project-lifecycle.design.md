# 项目生命周期与统一工作台

类型：设计 · 架构原则：已确认 · 详细需求与接口：待定义

[返回能力入口](README.md) · [架构决策](../../decisions/001-project-workspace.md)

## 目标与范围

在六阶段研发地图上增加跨流程生命周期能力，用统一 Project Workspace 连接目标、多人工作、上下游依赖、执行证据与交付。项目按自己的里程碑推进，可并行开展数据、模型与评测工作。

`AIGC_infra` 维护共用架构、规范、模板和平台设计。真实项目在各自现有仓库维护定义与知识，工作台自动汇总项目列表；大型项目可增加 Project Hub，长期汇总子能力的数据、方案、历次评测及结论，并链接各方向仓库中的证据。

## 输入、输出与关联

| 对象 | 定义与关联 |
| --- | --- |
| 项目 | 使用稳定 `project_id`，关联负责人、目标、仓库和里程碑；跨仓库时指定一个权威项目定义，其余仓库引用 |
| 工作项 | 按需要拆分可独立验收的子目标，使用 `task_id`；同一目标的参数尝试归入同一工作项 |
| 里程碑 | 定义阶段产物、验收条件和上下游依赖，关联工作项与证据 |
| 执行记录 | 数据处理、训练、评测或发布的一次运行；自动携带项目 ID，需要细分时携带工作项 ID |
| 资产与证据 | 关联代码版本、数据集、基准、模型、运行记录和评测结果，保存来源与版本引用 |
| 决策与交付 | 负责人确认继续、调整、停止或交付，记录理由并链接相关证据 |

基准配置引用固定的评测集与比较协议版本；一次评测结果关联模型、基准和运行配置。项目引用所选基线和验收要求，各执行平台产生对应事实。

## 三份长期文件起步

| 文件 | 人工维护的内容 |
| --- | --- |
| `project.yaml` | 项目 ID、负责人、目标、里程碑、依赖、验收要求或规则引用，以及基准和资产的稳定引用 |
| `README.md` | 问题背景、当前方案、重要结论及证据入口，承载人需要阅读的项目知识 |
| `AGENTS.md` | 如何采集、检查和汇总，哪些修订与判断需要负责人确认；具体验收条件由项目定义或引用规则承载 |

资产索引、验收规则或技术文档变复杂后按需拆分。普通运行明细由平台采集并关联，影响技术路线或交付决策的实验再补简短 MD，记录假设、结果、结论与证据。共用规范和模板统一维护，基准和资产以引用复用。

## Infra 用途与权威来源

| 能力 | 作用及信息归属 |
| --- | --- |
| Git 与项目规范 | 版本化目标、验收要求、技术知识和确认后的决策 |
| 平台接入与证据采集 | 从 Git、DLC、Dataset、Eval 及资产平台读取运行事实，建立项目关联并保留原始来源 |
| 规则校验与 Agent 汇总 | 检查证据是否满足验收条件，生成可追溯摘要和推进建议；字段、版本和指标等确定性检查由规则执行 |
| 统一工作台 | 读取可重建的汇总视图，展示项目状态、依赖、知识、实验、资产、变化和 DataViewer |

运行指标、检查结果和同步时间进入派生视图；`project.yaml` 保持稳定定义、负责人确认的状态及选定版本引用。大型项目的 Hub 汇总既有定义与证据。媒体与大量运行明细由源平台或存储管理。

```mermaid
flowchart LR
    A[项目目标与计划] --> B[数据 / 训练 / 评测 / 发布]
    B --> C[自动采集运行事实]
    C --> D[规则校验与 Agent 汇总]
    D --> E[工作台展示进展与证据]
    E --> F[负责人确认结论与下一步]
    F --> A
```

各平台事件、关键提交或约定周期可触发同步。Agent 汇总事实并提出建议，负责人确认技术结论、目标调整、决策与阶段推进。

## 验收原则

- 每项项目定义有明确维护位置，各阶段记录能通过稳定 ID 关联到项目与工作项。
- 工作台可追溯原始版本和证据，并分别呈现负责人确认的项目状态、自动验收结果、最近同步时间。
- 缺失、过期或不可访问的证据显示未知及原因；提交记录、作业完成和目标达成分别展示。
- 新结果通过采集与关联进入视图，日常进展由证据汇总；人工补充集中在目标、重要结论和决策。
